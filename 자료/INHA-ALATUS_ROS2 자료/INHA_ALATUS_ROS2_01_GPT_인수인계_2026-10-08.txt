02. 프로젝트 개념 및 최신 SW/Avionics 맥락
-------------------------------------------------------------------------------

[프로젝트 개념]
- INHA ALATUS는 Wing-Folding Fixed-Wing UAV 기술실증 프로젝트다.
- 큰 흐름은 사출/공중분리 → 날개 전개·고정 → 기본 고정익 비행 →
  Vision 기반 회수 검증이다.
- 현재 과제는 장거리 Waypoint/Loiter/YOLO 정찰을 구현하는 프로젝트가 아니다.
  그런 기능은 별도 후속 연구 항목이다.

[최신 결정 또는 명시된 현행 기준]
- Flight Controller: Pixhawk 6C (Pixhawk 6C Mini가 아님).
- Autopilot: PX4.
- 긴급 수동 조종 경로와 Ground Telemetry는 Pixhawk로 직접 연결한다.
  Raspberry Pi나 ROS를 거치도록 설계하지 않는다.
- Vision의 회수 표적은 '회수망 그 자체'가 아니라, 상대적으로 성긴
  Recovery Net 뒤에 설치된 양궁 과녁(Archery Target)이다.
  전방의 Net이 물리적으로 기체를 포획하는 구상이다.
- YOLO 학습은 별도 Desktop GPU에서 진행하고 온보드 장치에는 추론을
  배치한다는 방향이다.

[현재 우선 검토하는 탑재 구조: 실기체 시험 완료를 뜻하지 않음]
  Recovery Camera
      ↓
  Raspberry Pi 5 / Raspberry Pi OS 64-bit (Host)
      ├── Camera / libcamera / rpicam
      ├── AI HAT+ / Hailo Driver / HailoRT / YOLO Inference
      │       ↓ Detection metadata, Host ↔ Container IPC (방식 TBD)
      └── Docker: Ubuntu 22.04 ARM64 + ROS 2 Humble
              ├── Detection Bridge (개념/데모)
              ├── Target Tracker (향후 별도 구현·책임 경계 TBD)
              ├── Mission
              ├── Guidance
              └── MAVROS (향후 통합, 현 데모에는 없음)
                      ↓ MAVLink (향후)
                  Pixhawk 6C / PX4
                      ↓
                  Servo / ESC

별도 안전/지상 경로:
  RC Receiver ↔ Pixhawk 6C ↔ Servo/ESC
  QGroundControl ↔ Ground Telemetry Radio ↔ Pixhawk 6C

의미:
  - Pi OS/Hailo는 카메라 입력·YOLO 추론을 담당하도록 계획한다.
  - ROS 2는 인식 결과를 받아 Mission/Guidance를 판단한다.
  - PX4가 실제 비행안정화·Actuator 제어를 담당한다.
  - Pi 또는 ROS의 장애가 Pilot 긴급개입 경로의 단일 실패점이 되면 안 된다.
  - 이 TXT에서 항공 안전성/제어 안정성이 입증되었다는 뜻은 아니다.

'Camera Module 3'는 이번 Walkthrough 요청서의 Pi 환경 가정으로 제시되었다.
실제 기체 장착 및 정상 가동이 이번 실습에서 확인된 것으로 간주하지 않는다.
AI HAT+의 정확한 모델·드라이버 버전·호환성·설치 성과도 미검증이다.

04. FFF 학습·개발·이식의 3단계 목표
-------------------------------------------------------------------------------

[Phase A / PDF ①: 초기 개발환경]
- 개발 PC: Windows 11.
- Windows에 설치한 VS Code를 WSL 확장으로 사용한다.
- Linux 실행환경: WSL2 → Ubuntu 22.04 LTS.
- ROS 2: Humble.
- Windows UI에서 코드를 수정해도 Python/ROS 명령·빌드·테스트 실행은
  WSL Ubuntu Terminal 또는 VS Code의 WSL Terminal에서 수행한다.
- 개발 Workspace는 WSL 내부 Linux 파일시스템의 ~/alatus_ws.
- C:\ 의 일반 Windows 폴더나 /mnt/c를 ROS Workspace의 기본 위치로
  안내하지 않는다.
- 이 단계에 Docker, Hailo, PX4, Gazebo, MAVROS 설치는 포함하지 않는다.

PDF ① 주요 Chapter:
  0 전체 환경 구분 / 1 Windows 사전 점검 / 2 WSL 설치 /
  3 Ubuntu·Python·apt·Git / 4 VS Code WSL 연동 /
  5 ROS Humble 설치 / 6 Workspace·colcon / 7 Talker·Listener /
  8 최종 점검.

[Phase B / PDF ②: Mission/Guidance Python 실습]
- Starter Pack 5개 ROS 2 Python 패키지 사용.
- Mock archery-target Detection → Mission State → 표시용 Guidance.
- 실제 카메라/YOLO/Tracker/Pixhawk 없이 ROS 소프트웨어 흐름을 학습한다.
- 로깅·rosbag·통합 검사·순수 Python 단위 테스트를 수행한다.

06. 현재 데모의 ROS Topic 및 Message 계약 (최종 Baseline 아님)
-------------------------------------------------------------------------------

[Detection]
Topic: /alatus/target_detection
ROS type: std_msgs/msg/String
String.data 내용: JSON Object
Schema 식별자: alatus.demo.detection.v0
Publish: mock_target 또는 udp_detection_bridge 중 한 개만 활성화
Subscribe: mission_node, guidance_node

JSON 필드 (protocol.py의 실제 생성·검증 기준):
  schema       : 문자열 "alatus.demo.detection.v0"
  detected     : boolean
  class_name   : 문자열 "archery_target"
  confidence   : 숫자 [0.0, 1.0]
  center_x     : 숫자 [0, frame_width], 픽셀
  center_y     : 숫자 [0, frame_height], 픽셀
  bbox         : [x, y, width, height], 픽셀 단위, 좌상단 원점
  frame_width  : 0보다 큰 정수
  frame_height : 0보다 큰 정수
  timestamp    : 유한한 숫자, Unix epoch UTC seconds, 데모 wall clock
  source       : 비어 있지 않은 문자열 (예: mock, udp_mock)
  seq          : 0 이상의 정수

Schema/좌표 정의는 교육용 v0 계약이다. 최종 ROS Custom Message,
실제 Camera timestamp 정의, Image Frame/Body Frame/ENU/NED 규칙, QoS 등은
프로젝트 공통 Interface Freeze 전 TBD다. 현재 데모의 rclpy Publisher와
Subscriber는 대부분 create_publisher(..., 10), create_subscription(..., 10)
형태로 QoS depth=10을 전달하지만, 최종 운용 QoS Policy를 동결한 것이 아니다.

중요: 검증 함수는 bbox의 화면 범위와 숫자 유한성도 검사한다.
현재 valid_detection()은 bbox 중심좌표와 별도의 center_x/center_y가
기하학적으로 정확히 일치하는지까지 검사하지는 않는다. 필요해지면
테스트와 Schema 계약을 함께 강화해야 한다.

[Mission]
Topic: /alatus/mission_state
ROS type: std_msgs/msg/String (JSON)
Publish: mission_node
Subscribe: guidance_node
실제 Payload key:
  state     : WAITING / TARGET_DETECTED / TARGET_LOST / ABORT
  timestamp : publish 시 time.time() 수치
  seq       : 마지막 유효 Detection 순번, 없으면 -1
  source    : "mission_demo"

[Guidance '표시용 결과']
Topic: /alatus/guidance_decision
ROS type: std_msgs/msg/String (JSON)
Publish: guidance_node
Payload key:
  decision               : LEFT / RIGHT / ON_TARGET / HOLD
  timestamp              : publish 시 time.time() 수치
  source                 : "guidance_demo"
  flight_control_enabled : false
  seq                    : 현재 Detection 순번 또는 -1

주의: 이 구조는 'Detection Topic → Mission → Guidance'라는 개념적인
설명을 좀 더 정확히 표현하면 다음과 같다.

  mock_target OR udp_detection_bridge
      └─ /alatus/target_detection ────────────────┐
             ├── mission_node                      │
             │      └─ /alatus/mission_state ─┐   │
             └────────────────────────────────┼───┤
                                              ↓   ↓
                                         guidance_node
                                              ↓
                                     /alatus/guidance_decision

Guidance Node는 Mission State만으로 영상 중심 오차를 계산할 수 없다.
따라서 실제 코드에서도 Detection Topic을 별도로 직접 구독한다.

현재 코드에는 독립적인 target_tracker, 실제 detector_node,
'alatus_msgs', MAVROS Node, PX4 Interface, Servo Publisher가 없다.
'guidance_command' Topic도 이 실습의 구현된 Topic 이름이 아니다.
향후 제안 Architecture와 데모 구현을 혼동하지 마라.

-------------------------------------------------------------------------------
07. 데모 Mission/Guidance 로직 - 소스 기준 동작
-------------------------------------------------------------------------------

alatus_core/alatus_core/logic.py에 실제 정의:
- valid_detection(d)
- detection_fresh(d, now, timeout_s=1.5, future_tolerance_s=0.5)
- mission_decision(d, now, threshold=0.6, timeout_s=1.5)
- guidance_decision(d, state, now, threshold=0.6,
                    timeout_s=1.5, deadband_ratio=0.08)

각 숫자 0.6 / 1.5 s / 0.5 s / 0.08은 교육용 설정값이다.
실제 Vision 모델 성능 또는 고정익 제어설계로 검증된 수치가 아니다.

Mission 개념:
- 최초 Detection 전: WAITING.
- 유효하고 최신이며 detected=true, confidence >= threshold: TARGET_DETECTED.
- 미검출, 낮은 confidence, 잘못된 JSON, 만료 Detection: TARGET_LOST
  (첫 입력 이후/상태 변화에 따른 Node 로직 적용).
- mission_node의 abort_after_s가 양수이면 TARGET_LOST 연속 지속 시
  ABORT가 될 수 있다. 기본 설정은 abort_after_s=0.0이므로 비활성.
- 현재 ABORT는 '소프트웨어 상태 라벨'이다. 실제 기체의 긴급복귀 동작 아님.

Guidance 개념:
- Mission State가 TARGET_DETECTED가 아니면 HOLD.
- State가 일정시간 이상 갱신되지 않으면 HOLD.
- Detection과 Mission에서 수신한 seq가 다르면 HOLD.
- Detection 데이터 자체가 만료되거나 confidence가 낮으면 HOLD.
- 이상 없는 경우 이미지 내 수평 중심 위치를 정규화하여 판정한다.

실제 순수 함수에서 사용한 수평 오차:
  error = center_x / frame_width - 0.5
  error < -deadband_ratio → LEFT
  error > +deadband_ratio → RIGHT
  그 외 → ON_TARGET

기본 deadband_ratio=0.08이면:
  center_x < (0.5 - 0.08) × frame_width → LEFT
  center_x > (0.5 + 0.08) × frame_width → RIGHT
  그 외 ON_TARGET.

이 LEFT/RIGHT는 과녁이 '영상의 왼쪽/오른쪽'에 있다는 교육용
판단 표시이며 UAV가 실제로 그 방향으로 선회해야 한다는 검증된 명령이 아니다.

Node 구현 상 추가 세부사항:
- mission_node는 약 0.2초 주기로 상태를 Publish.
- guidance_node도 약 0.2초 주기로 판단 라벨 Publish.
- guidance_node는 mission_timeout_s=1.0초 기본 사용.
- Mock Node는 period_s=0.5초 기본 사용.
- 발행·수신 Node의 타이밍 또는 seq 불일치에 따른 일시적인 HOLD가
  정상적으로 나타날 수 있으므로 단일 샘플만 보고 실패로 판정하지 않는다.
- 동일 명칭 Topic에 Mock Publisher와 UDP Bridge를 동시에 사용하지 않는다.

Mock 입력 시나리오 (make_detection / mock_target 실제 구현):
  left     : image_width의 0.2 지점, detected=true, conf=0.95
  center   : 0.5 지점, detected=true, conf=0.95
  right    : 0.8 지점, detected=true, conf=0.95
  missing  : detected=false, conf=0.0
  low_conf : detected=true, conf=0.2
  stale    : timestamp = 현재시간에서 20초 이전

시나리오 cycle은 left → center → right → missing → low_conf → stale를
각각 4번 발행한 뒤 반복한다. Mock frame 기본값은 640×480 픽셀,
bbox는 64×64 픽셀이다. 모두 실제 카메라 측정값이 아니라 Mock Fixture다.

논리적 예측표 (로컬 순수 함수 기준 / ROS 실환경 확인 필요):
  left      : TARGET_DETECTED / LEFT
  center    : TARGET_DETECTED / ON_TARGET
  right     : TARGET_DETECTED / RIGHT
  missing   : TARGET_LOST     / HOLD
  low_conf  : TARGET_LOST     / HOLD
  stale     : TARGET_LOST     / HOLD

다른 물리 PC 사이의 ROS DDS 통신을 그대로 보장하는 설정이 아니다.

11. Phase C - Raspberry Pi 5 Docker로 소스만 이식하기

  docker --version
  docker compose version
  docker ps

<PI_USER>, <PI_IP>, <PACK_DIR>는 사용자 환경 확인 후 교체할 Placeholder다.
실제 사용자 이름이나 IP를 임의로 만들어 넣지 말아야 한다.

[WSL Ubuntu Terminal: Pi 접속·전달]
  export PACK_DIR="<PACK_DIR>"

GitHub나 프로젝트용 원격 Git Repository가 이미 있다고 가정하지 않는다.

[Pi OS Host Terminal: 신규 '독립형' Docker 데모]
  cd ~/alatus/ros2_demo/docker
  docker compose config
  docker compose up -d --build
  docker compose ps
  docker compose exec ros bash

이 신규 Compose의 실제 구성:
- Service: ros
- Image name: alatus-ros-humble:demo
- Base Docker image: ros:humble-ros-base-jammy
- Linux network_mode: host
- Env: ROS_DOMAIN_ID=42, ROS_LOCALHOST_ONLY=1
- Volume: ${HOME}/alatus/ros_ws → /workspace/alatus_ws
- command: sleep infinity
- restart: "no"

위 compose 설정은 실습을 위한 독립형 구성이다.
'자동으로 Mission 프로그램을 실행하고 고장 나면 재시작하는 최종 탑재 설정'
이 아니다. 실제 기존 ALATUS Compose 파일은 덮어쓰면 안 된다.
실제 ARM64 이미지 Pull/Build 지원은 사용자의 Pi에서 확인해야 한다.
Docker의 Ubuntu는 별도 Ubuntu Kernel이 아니라 Pi OS Host의 Linux Kernel을
공유하는 Ubuntu 22.04 기반 Userspace다.

주의: 현재 신규 Dockerfile에서 명시적으로 추가하는 ROS 패키지는

라고 말하면 안 된다. 필요시 정확한 의존성을 확인하여 Dockerfile을
수정하고 재빌드·검증해야 한다.

이 Sender는 실제 Camera나 Hailo가 아닌 Host 측 Synthetic JSON 전송기다.
Bridge 또한 기존 ALATUS Starter Kit의 미확인 Bridge와 동일한 것으로
간주할 수 없다. 기존 Starter Kit이 쓰는 UDP Port, Schema, Topic Type,
BBox 좌표·타임스탬프·source를 반드시 비교해야 한다.

기존 Kit 경로로 '전달받은' 정보:
  docker/Dockerfile
  docker/compose.yaml
  ros_ws/tools/udp_detection_bridge.py
  vision/scripts/mock_sender.py

이는 기존 ZIP을 직접 열어 확인한 파일 목록이 아니다.
실제 파일에서 경로/서비스명/Schema가 다르면 사용자의 파일을 우선한다.

'ROS_LOCALHOST_ONLY=1'과 'network_mode: host'는 Linux Pi Host 안에서
이 로컬 UDP 예제를 구성하기 위한 설정이다. 이 설정을 무작정 별도 PC와의
분산 ROS 통신에 적용하면 안 된다.

17. 다른 GPT가 실제 답할 때 지켜야 할 형식

사용자가 학습·개념 질문을 하면:
- 간결한 개념 → 이 프로젝트에서의 위치/역할 → 관련 실제 파일/Topic

사용자가 '다음 단계'를 물으면:
- 사용자가 완료했다고 알려준 단계까지만 전제로 삼는다.
- 현재 실행환경과 마지막 성공 명령을 확인하고 한 단계씩 진행한다.
- 다음 단계 명령을 제공할 때 환경, 명령, 기대 출력, 오류대응을 포함한다.
- 실습과 관계없는 Gazebo/PX4 설치를 갑자기 끼워 넣지 않는다.

사용자가 에러/로그를 주면:
- 에러 본문에서 확인되는 사실부터 추출한다.
- 환경(`cat /etc/os-release`, `uname -m`, `echo $ROS_DISTRO`, etc.)과
  패키지/인터프리터·경로를 확인한 뒤 원인을 범위 좁혀 판단한다.
- 관찰한 로그와 추측한 가능성은 문장으로 분리한다.
- 문제 해결 과정에서 기존 정상 파일을 무작정 삭제/덮어쓰지 않는다.

사용자가 새 코드/노드/ROS Message를 요청하면:
- 현재 Topic 계약과 호환되는 버전인지 또는 Schema 변경이 필요한지 설명.
- 실제 컴파일/실행은 하지 못했다면 테스트 코드를 주더라도 '미검증' 표시.
- 새로운 alatus_msgs/Tracker/MAVROS 관련 기능은 '새 구현안'으로 표시.
- 실제 비행제어 권한 활성화와 로깅 전용 교육용 기능을 엄격히 구분.

사용자가 Pi 이식을 물으면:
- src만 전송, ARM64 재빌드, ROS 의존성 설치, Compose Volume 실물 확인.
- 기존 Kit 구조 확인 후 Merge 필요성을 검토한다.
- WSL과 Pi에서 동일한 Pure Python 입력/결과 비교를 우선 적용한다.

출력에 사용할 추천 구분 레이블:
  [확정] [계획] [데모 구현] [예시값] [TBD] [검증 완료: 테스트 범위]
