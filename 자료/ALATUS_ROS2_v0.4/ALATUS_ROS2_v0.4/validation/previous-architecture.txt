# INHA ALATUS ROS 2 시스템 아키텍처 설계안 v0.1

**목표\:** Gazebo의 고정익 시뮬레이션과 실제 Pixhawk 6C 기반 고정익 UAV에서 최대한 동일한 ROS 2 Mission/Guidance 소프트웨어를 구동할 수 있는 구조를 설계하고, 이를 3명이 병렬로 개발할 수 있도록 업무를 분배합니다.

먼저 중요한 결론부터 말씀드리겠습니다.

**3명이 처음부터 10개가 넘는 Node를 각각 개발하는 것보다, 핵심 기능을 3개 Workstream으로 나누고 공통 인터페이스를 먼저 고정하는 것이 좋습니다.**

아래 설계는 현재 ALATUS의 요구조건에 근거하지만, 실제 기체 제어까지 검증 완료된 시스템은 아닙니다. **구현할 항목, 기존 교육용 코드에서 재사용할 항목, 아직 결정되지 않은 항목**을 구분하겠습니다.

## 1\. 전체 소프트웨어 구조

## ALATUS · Proposed ROS 2 Architecture

실선은 기본 데이터 흐름, 역할별 묶음은 3인 담당 영역입니다. PX4 제어 송신은 초기 비활성입니다.

**A · Perception &amp; Tracking**

**B · Mission &amp; Guidance**

**C · PX4 Interface &amp; Integration**

기본값: Shadow / 제어 송신 금지

**PX4 SITL**

Real Aircraft

PX4 State Adapter가 제공하는 비행상태는 Mission과 Guidance 양쪽으로 전달됩니다. Logging/Health Monitoring은 전체 구성을 관찰하는 공통 기능으로 추가합니다.

이 구조에서 실제 제어계 개발의 핵심은 B와 C 사이입니다.

B는 **어떻게 비행경로를 보정할지 계산**하고, C는 **그 요청이 실제 PX4에서 사용할 수 있는 형식인지, 현재 명령을 전달해도 되는지 판단**합니다.

이렇게 분리해야 시뮬레이션 검증 단계와 실기체 통합 단계에서 안전하게 기능을 추가할 수 있습니다.

## 2\. 어떤 ROS 2 Node가 필요한가?

처음부터 모두 구현하는 대신, 필수 Node 7개와 후속 확장 Node 3개로 구분하겠습니다.

| Node | 역할 | 우선순위 | 담당 |
|--------|--------|--------|--------|
| `detection_bridge_node` | Mock/YOLO 결과를 ROS 2로 변환 | 필수 | A |
| `target_tracker_node` | 과녁 추적 및 유효성 관리 | 필수 | A |
| `mission_manager_node` | Recovery 상태기계 운용 | 필수 | B |
| `guidance_node` | Guidance 제안값 계산 | 필수 | B |
| `px4_state_adapter_node` | PX4 비행상태 수신 및 변환 | 필수 | C |
| `safety_gate_node` | 명령 허가 및 안전조건 확인 | 필수 | C |
| `px4_command_adapter_node` | PX4 인터페이스와 출력 연결 | 필수, 초기 송신 금지 | C |
| `system_health_node` | Node·통신·데이터 상태 감시 | 확장 | C |
| `recovery_supervisor_node` | 회수 절차의 세부 운영 조정 | 확장 | B |
| `flight_logger_node` | 시험 데이터 통합 기록 | 확장 | 공동 |

`flight_logger_node`는 처음에는 없어도 됩니다. ROS 2의 `rosbag2`와 각 Node의 로깅으로 시작할 수 있습니다.

또한 `recovery_supervisor_node`를 별도로 만들기 전에는 그 기능을 `mission_manager_node`에 포함하는 것이 좋습니다. 기능이 많아지면 나중에 분리하면 됩니다.

### 기존 Starter Pack에서 재사용할 부분

현재 교육용 Starter Pack의 패키지는 `alatus_core`, `alatus_mock`, `alatus_mission`, `alatus_guidance`, `alatus_bringup`입니다.

이 코드를 버리고 새로 시작할 필요는 없습니다.

`alatus_mock`은 A 담당의 Mock/Bridge 개발 기반으로, `alatus_core`와 `alatus_mission`, `alatus_guidance`는 B 담당의 상태기계와 판단 로직 기반으로, `alatus_bringup`은 C 담당의 통합 Launch 기반으로 활용할 수 있습니다.

단, 기존 `std_msgs/String` JSON은 **교육용 인터페이스**입니다. 다음에 제안하는 Custom Message 구조로 전환하려면 양쪽 Node가 동시에 호환되도록 수정해야 합니다.

## 3\. Topic과 Message 설계

여기가 세 사람의 코드가 만나는 계약서입니다.

**Topic 이름뿐 아니라 Message 타입, 단위, 좌표계, Timestamp, 유효성 조건까지 정의해야 합니다.**

다음은 ALATUS용 Interface Draft v0.1입니다. 아직 프로젝트 확정 Baseline은 아닙니다.

| Topic | Message 제안 | Publisher → Subscriber |
|--------|--------|--------|
| `/alatus/detection` | `TargetDetection` | Bridge → Tracker |
| `/alatus/target_track` | `TargetTrack` | Tracker → Mission, Guidance |
| `/alatus/aircraft_state` | `AircraftState` | PX4 Adapter → Mission, Guidance |
| `/alatus/operator_request` | `OperatorRequest` | UI/시험 → Mission |
| `/alatus/mission_state` | `MissionState` | Mission → Guidance, Safety |
| `/alatus/guidance_proposal` | `GuidanceProposal` | Guidance → Safety, Logger |
| `/alatus/safety_status` | `SafetyStatus` | Safety → Mission, Logger |
| `/alatus/system_health` | `SystemHealth` | Health → Mission, Logger |

### 메시지 설계에서 반드시 지킬 규칙

**첫째, Detection과 Tracking을 구분합니다.** YOLO가 한 프레임에서 과녁을 찾았다는 사실과 시간적으로 안정적인 Target Track을 확보했다는 사실은 다릅니다.

**둘째, Mission과 Guidance를 분리합니다.** Mission이 유도 허가를 내리지 않았다면 Guidance가 계산한 제안값이 있어도 실제 제어 요청으로 전달하지 않습니다.

**셋째, 실제 기체 상태를 Guidance 입력으로 사용합니다.** 과녁의 픽셀 좌표만으로 제어계를 구성하지 않습니다.

**넷째, Timestamp와 데이터 유효기간을 기록합니다.** 오래된 데이터를 새로운 정보처럼 사용하지 않도록 해야 합니다.

## 4\. Custom Message의 구체적인 예시

### A가 제공할 TargetTrack

```text
# TargetTrack.msg — 설계안
std_msgs/Header header

bool valid
float32 confidence

float32 center_x_norm
float32 center_y_norm

float32 width_norm
float32 height_norm

uint32 track_id
```

`center_x_norm`과 `center_y_norm`은 각각 0\~1의 영상 정규화 좌표로 정의합니다.

이 메시지는 과녁의 영상상 위치와 Tracking 결과를 나타냅니다. 이것만으로 과녁까지의 실제 거리나 3차원 위치가 확보된 것은 아닙니다.

`valid=false`인 경우에도 최신 추적 상태를 명시적으로 발행하도록 설계할 수 있습니다. 다만 데이터 자체의 발행이 중단되면 수신 Node가 Timeout을 별도로 검출해야 합니다.

### C가 제공할 AircraftState

```text
# AircraftState.msg — 설계안
std_msgs/Header header

bool state_valid
bool armed
bool manual_override_active

float32 airspeed_mps
float32 ground_speed_mps

float32 roll_rad
float32 pitch_rad
float32 yaw_rad

float32 relative_altitude_m
uint8 navigation_state
```

이 메시지는 Mission/Guidance에 필요한 정보만 모은 추상화 계층입니다.

PX4로부터 모든 필드를 항상 수신할 수 있다는 뜻은 아닙니다. 특히 대기속도 센서가 없다면 `airspeed_mps`를 유효한 측정값처럼 사용해서는 안 됩니다.

실제 구현에서는 필드별 유효성이나 상태추정 품질을 추가하는 방식을 권장합니다.

### B가 제공할 GuidanceProposal

여기서는 실제 제어 입력 형식이 아직 확정되지 않았으므로 PX4 명령과 분리합니다.

```text
# GuidanceProposal.msg — 설계안
std_msgs/Header header

bool valid
bool control_requested

uint8 guidance_mode

float32 target_bearing_error_rad
float32 requested_path_correction_rad

string reason
```

`requested_path_correction_rad`는 향후 비행역학 검토를 거쳐 정의할 Guidance 출력 후보입니다. 초기에는 실제 제어명령이 아니라 \*\*제안값(Proposal)\*\*으로만 기록합니다.

이 값의 정의, 부호규약, 제한 범위는 실제 제어기 설계와 함께 확정해야 합니다.

특히 `control_requested=true`는 명령 허가를 의미하지 않습니다. Safety Gate가 별도의 조건을 확인해야 합니다.

## 5\. 실제로 작동하는 제어계를 만들려면 무엇이 더 필요한가?

이 부분이 가장 중요합니다.

Node와 Topic을 모두 연결했다고 해서 실제 제어계가 완성되는 것은 아닙니다. **제어계는 센서 정보를 이용해 목표와 현재 상태의 차이를 계산하고, 그 차이를 줄이도록 항공기의 움직임을 변화시키는 폐루프(Closed-loop) 시스템**입니다.

ALATUS에서는 세 개의 계층으로 구분해야 합니다.

### 고정익 UAV의 계층형 제어 구조

**Guidance — ROS 2**

어느 경로로 이동해야 목표를 만족하는가?

**Flight Control — PX4**

요구한 비행상태를 어떻게 추종하는가?

**Aircraft Dynamics — Gazebo / 실기체**

조종면과 추력에 항공기가 어떻게 반응하는가?

센서 및 상태추정 → 상위 제어계로 피드백

실제로 작동하는 시스템을 만들기 위해 필요한 개발 작업을 여섯 단계로 분해하겠습니다.

### 5.1 비행 상태를 확보한다

PX4에서 다음 상태를 ROS 2로 받아야 합니다.

- Position / Velocity / Attitude
- Flight Mode / Armed State
- 상태추정 유효성
- Airspeed 등 이용 가능한 속도 정보
- 수동개입 상태 및 통신 상태

PX4 uXRCE-DDS를 사용한다면 `/fmu/out/vehicle_status`, `/fmu/out/vehicle_attitude`, `/fmu/out/vehicle_local_position` 등의 Topic을 검토할 수 있습니다. 실제 사용 가능 여부는 해당 PX4 버전의 `dds_topics.yaml`로 확인해야 하며, ROS 2 메시지의 QoS와 PX4 메시지 버전도 맞춰야 합니다. citeturn172626search0turn172626search1

이 데이터를 `px4_state_adapter_node`에서 읽어 `/alatus/aircraft_state`로 변환합니다.

### 5.2 Guidance의 목표를 수학적으로 정의한다

처음에는 이미지에서 과녁이 얼마나 벗어났는지 계산합니다.

\[
e_x=\frac{u_t-u_c}{W}
\]

- \(u_t\)\: 과녁 중심의 가로 픽셀 좌표
- \(u_c\)\: 영상 중심의 가로 픽셀 좌표
- \(W\)\: 영상 너비

이 값은 **정규화된 영상오차**이지, 비행경로 오차나 Heading Error와 동일한 물리량이 아닙니다.

실제 Guidance를 설계하려면 다음 질문에 답해야 합니다.

| 결정할 사항 | 이유 |
|--------|--------|
| 과녁이 기체 기준 어느 방향에 있는가? | 카메라 좌표와 기체 좌표 변환 |
| 과녁까지 거리를 알고 있는가? | 경로 및 시간 계획에 필요 |
| 현재 속도와 비행상태는 무엇인가? | 고정익 선회·기동 가능성 평가 |
| 어떤 Guidance 법칙을 사용할 것인가? | 목표 추종 경로 생성 |
| PX4에 어떤 물리량을 요구할 것인가? | 제어 인터페이스 결정 |

제어 알고리즘 후보에는 경로 추종 기반 유도법, 시선각 기반 기법, 비례항법 계열의 접근법 등이 있습니다.

다만 **ALATUS에 어떤 방법이 적합한지는 아직 확정할 근거가 부족합니다.** 공력특성, 속도 범위, 시야각, 카메라 지연, 회수망 치수와 접근조건이 필요합니다.

처음부터 특정 Guidance Gain을 정하지 않는 이유입니다.

### 5.3 PX4가 지원하는 제어 인터페이스를 선택한다

이번 설계에서는 ROS 2–PX4 연결의 우선 검토안으로 **uXRCE-DDS + PX4 ROS 2 Interface Library**를 제안합니다.

PX4 공식 문서에서는 ROS 2 Interface Library를 통한 External Mode 구현을 지원하며, 고정익용 제어 인터페이스도 버전에 따라 제공하고 있습니다. 특히 `FwLateralLongitudinalSetpointType`은 PX4 v1.17부터 지원하는 기능이므로, 이전 버전의 PX4에 있다고 가정하면 안 됩니다. citeturn172626search0turn268292search3

현재 프로젝트에서 이전에 사용했던 PX4 Commit과 펌웨어 버전을 먼저 확인해야 합니다.

**중요\:** PX4에서는 ROS 2 Offboard 제어 시 Setpoint 충돌을 방지해야 합니다. 공식 문서에서도 올바른 비행모드에서만 외부 Setpoint를 발행하고, Offboard 신호가 중단되었을 때의 Failsafe를 설정하도록 요구합니다. citeturn268292search0

그래서 C 담당자의 `px4_command_adapter_node`가 B의 출력값을 무조건 전달하게 만들어서는 안 됩니다.

### 5.4 Safety Gate를 구현한다

Safety Gate는 ROS 2 프로그램의 판단과 실제 비행제어 명령 사이에 위치해야 합니다.

다음 조건을 확인하는 구조를 제안합니다.

- 현재 Mission이 Guidance를 허용하는가?
- 기체가 요구되는 상태에 있는가?
- Target 데이터가 유효하고 충분히 최신인가?
- 기체 상태추정 정보가 유효한가?
- 통신 연결 및 명령 인터페이스가 정상인가?
- 운영자가 허가한 시험 모드인가?
- 데이터 불일치나 Timeout이 발생하지 않았는가?

한 가지라도 중요 조건이 만족되지 않으면 명령을 전달하지 않습니다.

다만 이 Gate는 **PX4의 Failsafe를 대체하지 않습니다.** PX4의 수동개입·Offboard Loss·비행모드 복구 기능을 독립적으로 설정하고 검증해야 합니다.

### 5.5 비행체 모델을 만든다

Gazebo에서 ALATUS를 실제처럼 움직이려면 고정익의 동역학과 공력특성을 구현해야 합니다.

초기에는 PX4 공식 `gz_advanced_plane` 모델을 이용해 소프트웨어와 비행제어 인터페이스를 검증하는 것이 좋습니다. PX4 공식 문서에서도 Advanced Plane 모델을 제공하며 일반 Plane과 공력 모델 구성에 차이가 있다고 설명합니다. citeturn268292search1

그 이후 다음 데이터를 이용하여 ALATUS 전용 시뮬레이션 모델을 개발해야 합니다.

- 실제 기체의 질량과 CG
- 관성모멘트
- 주익 및 꼬리날개의 공력특성
- 조종면 효과
- 추진계 특성
- 센서 배치
- 사출/전개 후 초기조건

특히 ALATUS는 Wing-Folding 기체이므로 날개가 전개되지 않은 과도상태와 정상 고정익 비행 상태를 구분해야 합니다.

초기 ROS 2 개발은 **주익 전개와 Lock이 완료된 정상 고정익 상태**를 가정해서 진행하겠습니다.

### 5.6 Closed-loop Simulation을 검증한다

여기까지 개발했다면 다음 과정으로 넘어갑니다.

1. PX4 SITL + Gazebo에서 정상 고정익 비행을 확인한다.
2. ROS 2가 기체 상태를 정상적으로 수신하는지 확인한다.
3. Mock Target 입력에 따라 Guidance Proposal이 변화하는지 확인한다.
4. Shadow Mode로 실제 비행에 적용하지 않고 Proposal과 기체 상태를 기록한다.
5. 제어기·안전조건을 검증한 뒤, 별도로 승인된 SITL 환경에서만 제한적인 명령 송신을 시험한다.
6. 목표 추종 오차와 기체 응답, 실패 시 Failsafe 동작을 분석한다.

**여기서 5\~6단계가 성공해야 비로소 통합 폐루프 제어계가 작동한다고 말할 수 있습니다.** 현재의 Mock LEFT/RIGHT 출력만으로는 그 단계에 도달했다고 볼 수 없습니다.

# 6\. ROS 2 개발자 3명 업무 분배

이번에는 기존 팀 전체 조직을 바꾸는 것이 아니라, **ROS 2 시스템 개발에 참여할 3명의 세부 역할**을 정의하겠습니다.

기존 FFF가 Mission &amp; Guidance 책임자라는 점을 유지하고, 나머지 두 명은 각각 Perception/Tracking 인터페이스와 PX4/Simulation Integration을 담당하는 구조를 제안합니다. 이 두 역할은 기존 Vision, DDD+EEE, GGG 담당자와 협업해야 하며 그들의 업무를 자동으로 대체하는 것은 아닙니다.

## 담당자 A — Perception &amp; Tracking

(Workstream A)

주요 목표: 어떤 환경에서든 Mission이 동일한 Target 데이터를 받도록 구현

**구현할 기능**

- `detection_bridge_node`
- `target_tracker_node`
- Mock Detection 및 실제 YOLO 인터페이스 변환
- Target 유효성, Timestamp, 추적 중단 처리

**산출물\:** `alatus_perception` 패키지, Detection/Track 메시지 명세, Mock 시나리오, 자동 테스트

**완료 기준\:** Mock 좌·우·중앙·미검출·오래된 데이터에 대해 올바른 Tracking 출력을 발행

## 담당자 B — Mission &amp; Guidance (FFF)

(Workstream B)

주요 목표: ALATUS의 회수 임무를 상태기계로 구성하고 Guidance Proposal을 계산

**구현할 기능**

- `mission_manager_node`
- `guidance_node`
- Recovery Mode 상태전환
- Target Lost, Abort, Guidance Enable
- 초기 영상오차 계산 및 향후 Guidance 알고리즘 설계

**산출물\:** `alatus_mission`, `alatus_guidance` 패키지, 상태전이도, Guidance 설계 문서, Unit Test

**완료 기준\:** Target/기체 상태에 따라 Mission이 전환되고 유효한 Guidance Proposal 또는 HOLD를 출력

## 담당자 C — PX4 Interface &amp; Integration

(Workstream C)

주요 목표: Gazebo·PX4에서 상태를 읽고 ROS 2 전체 시스템을 연결하며 안전하게 검증

**구현할 기능**

- `px4_state_adapter_node`
- `safety_gate_node`
- `px4_command_adapter_node`의 Shadow Mode
- ROS 2 ↔ PX4 통신
- Launch, rosbag2, 통합시험 및 환경 설정

**산출물\:** `alatus_px4_interface`, `alatus_safety`, `alatus_bringup`, SITL 연결 기록, 통합시험 결과

**완료 기준\:** 실제 PX4 SITL 상태를 ROS 2에서 수신하고 Mission/Guidance/Safety/Logger까지 데이터가 연결됨

## 7\. 3명이 동시에 개발하려면 인터페이스를 먼저 고정해야 한다

가장 많이 발생하는 소프트웨어 협업 문제는 각자 작성한 Node가 작동하지만 서로 연결되지 않는 것입니다.

예를 들어 A는 `center_x`를 픽셀 단위로 발행하고 B는 0\~1 정규화 좌표라고 가정하면 코드상 오류가 없더라도 결과가 틀릴 수 있습니다.

따라서 다음 인터페이스 항목을 공통으로 합의해야 합니다.

| 항목 | v0.1 결정 제안 | 최종 확정 필요 |
|--------|--------|--------|
| ROS Version | Humble | 현재 Baseline 유지 |
| Target 좌표 | 정규화 이미지 좌표 | 카메라 기준 및 부호 |
| 자세각 | rad | 좌표계 명시 |
| 속도 | m/s | Ground/Air 구별 |
| Time | ROS Header + 수신 시각 | Sim/Real Clock 정책 |
| Mission State | 명시적 enum | 전이 조건 |
| Safety 상태 | 허가/차단 + 이유 | PX4 상태와 매핑 |
| QoS | Topic별 지정 | PX4 및 센서 인터페이스 확인 |
| 명령 송신 | 초기 Disabled | SITL Gate Review 후 허가 |

추가로 사용자 정의 ROS 메시지는 `alatus_msgs`라는 독립된 Interface Package로 만들 것을 제안합니다. 패키지 소유권은 B가 담당하되, **A·B·C가 공동 검토한 뒤 변경하는 방식**이 좋습니다.

메시지 형식은 공통 파일이므로 특정 담당자가 임의로 수정하면 나머지 두 명의 코드가 동시에 깨질 수 있습니다.

# 8\. 개발 일정 및 단계별 산출물

현재 ROS 2 기초 개념을 공부한 단계라는 점을 고려해 **6주 실행계획**을 제안합니다.

이 일정은 확정된 프로젝트 일정이 아니라 개발 난이도를 고려한 계획입니다. 특히 실제 Guidance 폐루프 성능 검증이나 비행시험까지 6주 내에 끝난다고 보장하는 일정은 아닙니다.

| 주차 | A: Perception | B: Mission/Guidance | C: PX4/Integration |
|--------|--------|--------|--------|
| W1 | Mock/Bridge 및 Track 메시지 | Mission State Machine | PX4 SITL 상태 수신 |
| W2 | Tracker·Timeout 구현 | Guidance Proposal | Safety Gate·Launch |
| W3 | Detection/Track 통합시험 | Mission/Guidance Unit Test | 전체 Topic 통합 |
| W4 | 가상/실제 입력 교체시험 | 기체상태 반영 Guidance 설계 | Gazebo Shadow Mode |
| W5 | Tracking 지연·유효성 평가 | Guidance 성능 분석 | SITL 인터페이스·Failsafe 검증 |
| W6 | 테스트 보완 | Guidance 알고리즘 개선 | 통합 리포트 및 Pi 이식 준비 |

### 공통 통합 Gate

(G1)

**W1 종료 — 공통 메시지 및 기본 Node 확정**

3명 모두 같은 Workspace에서 서로의 메시지를 읽을 수 있어야 합니다.

---

(G2)

**W3 종료 — ROS 2 논리 시스템 통합**

Mock → Tracking → Mission → Guidance → Safety까지 데이터 흐름이 정상이어야 합니다.

---

(G3)

**W4 종료 — PX4/Gazebo Shadow Mode 통합**

PX4 상태 수신, Mission 판단, Guidance Proposal, 로그 기록을 검증합니다. 이때 실제 제어명령은 적용하지 않습니다.

---

(G4)

**후속 승인 단계 — Closed-loop SITL**

Guidance 법칙, PX4 지원 인터페이스, 안전 조건 및 복구 동작 검토 후 별도 수행합니다.

---

# 9\. Gazebo에서 반드시 수행해야 할 통합시험

최종적으로 소프트웨어를 실제 고정익기에 적용하려면 단순 정상 상황만 시험하면 부족합니다.

최소한 다음 시험을 계획해야 합니다.

| 시험 ID | 시험 상황 | 기대 동작 |
|--------|--------|--------|
| T01 | 정상 Target Detection | Mission에서 Target 관련 상태 활성화 |
| T02 | 과녁 미검출 | 유효한 Guidance 차단 |
| T03 | 낮은 Confidence | 해당 입력 무효 처리 |
| T04 | 오래된 Timestamp | Stale Data로 처리 |
| T05 | Detection Node 종료 | Timeout 감지 및 안전 상태 전환 |
| T06 | ROS 2–PX4 통신 중단 | PX4 자체 Failsafe와 ROS 상태 이상 처리 확인 |
| T07 | 비행모드 불일치 | Guidance 제어 허가 차단 |
| T08 | Operator Abort | Guidance 중단 및 지정된 안전 절차 요청 |
| T09 | Camera 지연 증가 | 지연 감지·유효성 판단 |
| T10 | 정상 고정익 Shadow Mode | Guidance Proposal과 기체 응답 로그 확보 |
| T11 | 제어 인터페이스 검증 | 승인된 SITL에서만 제한 명령 송신 |
| T12 | 통합 시스템 재시작 | Node 및 통신이 정의된 순서로 복구 |

T06의 PX4 Failsafe나 T08의 안전 절차는 실제로 구성된 PX4 모드와 시험환경에 따라 달라지므로, 결과를 미리 특정해서는 안 됩니다.

각 시험마다 최소한 `Test ID`, `입력 조건`, `기대 결과`, `실제 로그`, `PASS/FAIL`, `시험 환경 및 버전`을 기록해야 합니다.

# 10\. 당장 시작할 첫 번째 공동 작업

지금 팀이 해야 할 가장 우선적인 일은 `Guidance Algorithm`을 복잡하게 작성하는 것이 아닙니다.

**먼저 공통 메시지와 Node 연결을 구현하는 것입니다.**

기존 Starter Pack을 기반으로 다음 목표부터 시작하면 됩니다.

**첫 번째 통합 목표** (ROS 2 Only)

Mock Detection / Tracking — A

Mission State Machine — B

Guidance Proposal — B

Safety Gate / Logger — C

첫 통합에서는 Mock Aircraft State를 사용할 수 있습니다. 이후 C가 실제 PX4 SITL 상태 입력으로 교체합니다. Guidance Node는 Target 정보와 Mission 상태를 모두 직접 받아야 합니다.

### 첫 번째 업무 배분은 이렇게 시작하는 것이 좋겠습니다.

- **A\:** 기존 Mock Detection을 이해하고, 데이터 검증 및 Target Tracking Node를 추가합니다.
- **B(FFF)\:** 기존 Mission/Guidance 로직을 State Machine과 공통 메시지 기반으로 정리합니다.
- **C\:** 기존 Bringup을 확장하고, PX4 SITL 상태 수신 및 통합 로그를 구현합니다.

최초 통합 시점에는 PX4로 제어명령을 보내지 않습니다.

3명이 모두 자신의 기능을 구현한 뒤 하나의 Launch 파일로 시작하여, 터미널에서 Topic과 State Transition을 확인하는 것을 첫 번째 성공 기준으로 삼습니다.

## 11\. 실제 구현 전에 확정해야 할 기술 항목

다음 항목은 아직 확인되지 않았거나, 검토 후 결정해야 합니다.

**PX4/Gazebo 버전\:** 기존에 사용한 `gz_advanced_plane` 및 PX4 Commit을 기준으로 사용 가능 인터페이스를 확인해야 합니다. PX4 Main과 안정 릴리스의 기능을 혼용하지 않겠습니다.

**Guidance 알고리즘\:** 아직 항공기의 공력성능, 속도 및 회수 조건이 확정되지 않았으므로 실제 제어 Gain이나 제어명령을 정할 수 없습니다.

**카메라 및 영상 좌표계\:** Camera FOV, 영상 해상도, Camera-Body 변환 및 지연 측정 기준을 정해야 합니다.

**전개 상태 피드백\:** Wing Lock 완료 여부를 소프트웨어에 전달할 센서나 신뢰 가능한 상태 정보가 필요한지 검토해야 합니다.

**Safety 및 Authority\:** 실제 제어 권한의 주체는 PX4와 운용자이며, ROS 2 Safety Gate는 상위 수준의 추가 검증 계층입니다. 두 계층의 동작을 별도로 시험해야 합니다.

## 최종 제안

INHA ALATUS의 ROS 2 개발은 **A: Perception &amp; Tracking, B: Mission &amp; Guidance, C: PX4 Interface &amp; Integration**의 세 영역으로 분담하는 것이 좋습니다.

다만 세 영역의 개발 목표는 각각 독립적인 프로그램 세 개를 만드는 것이 아니라, **공통 Message를 기반으로 하나의 통합 소프트웨어를 만드는 것**입니다.

현재 단계에서는 다음 세 가지를 우선 완성해야 합니다.

1. **공통 인터페이스 v0.1\:** Node, Topic, Message, 좌표계 및 Timestamp 명세
2. **Mock 기반 ROS 2 통합 시스템\:** Target → Mission → Guidance → Safety
3. **PX4/Gazebo 상태연동\:** 실제 SITL 상태를 받아 Shadow Mode로 전체 동작 검증

그 이후 비행역학에 맞는 Guidance 설계와 Closed-loop SITL 검증으로 확장해야 합니다.

**이 세 가지가 완료되면 ROS 2의 기초 개념을 공부하는 단계를 넘어, 실제 ALATUS 고정익기의 제어계 개발에 필요한 소프트웨어 통합 기반을 확보하게 됩니다.**
